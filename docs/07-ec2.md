# EC2 instances (experimental)

EC2 is a second backend. Use it when you need a VM rather than a cluster. CS Bridge launches an EC2 instance and opens
VS Code on it. The session runs on that instance. No Slurm job is involved. The backend implements the `Backend`
contract in [Backends and transports](05-backends-and-transports.md#backend).

## Model

An EC2 session is an ordinary session record with an `ec2` field. The field holds region, instance type, image, login
user and public IP.

- Its `alias` is `aws-<region>` and its `jobId` is the instance id.
- Storage, cross-window sync, heartbeats, the per-session SSH host, remote-window detection and the card's actions
  therefore use the same code as for Slurm sessions.
- It is reached over plain SSH, with no Linkspan and no tunnel.
- Ending a run records nothing in Run History.

## Sign-in

The EC2 API calls are in `ec2.ts`, which does not import `vscode`. Sign-in is in `aws.ts`:

- Input boxes take the access key id, secret and optional session token.
- They are kept in SecretStorage under `aws.credentials` and restored on activation. A key AWS refuses is deleted.
- The first call, `DescribeRegions` against `us-east-1`, lists the account's regions.
- AWS calls time out after 5 s to connect and 15 s per request.
- **Sign Out of AWS** deletes `aws.credentials` and this window's key. Until this window's next sign-in:
  - this window's EC2 polls hold;
  - Start fails with "Sign in to AWS first.";
  - Delete of a launched instance in this window fails with the same message;
  - a Stop that this window carries out as the session's owner fails with the same message;
  - a Stop asked here for a session another window owns uses that window's key.

  Other open windows keep their key until they reload. **Create Cloud VM** is offered only while signed in.
- Only the menu items depend on `csbridge.experimentalFeatures`. A stored key is restored and EC2 sessions are driven
  either way.

## Catalogue

`models.ts` lists ten `t3` and `m5` instance types. It lists two images:

- Amazon Linux 2023 (user `ec2-user`);
- Ubuntu 24.04 LTS (user `ubuntu`).

## Lifecycle

1. **Create.** The menu's **Create Cloud VM** pages pick region, instance type and image. The record is saved as
   `not_started`. No instance exists yet.
2. **Start.** There is no script preview. Start submits at once.
   - An instance that still exists and is not `shutting-down` or `terminated` is restarted with `StartInstances`.
   - Otherwise a new one is launched with `RunInstances`. It uses `resolve:ssm:` to get the image's latest AMI.

   Before the first launch in a region after each sign-in, Start makes sure the region has a default VPC. It creates
   one if the account has none. Then it sets up the following, in parallel:
   - A security group `CS-Bridge SSH Access` that opens TCP port 22 to `0.0.0.0/0`. It is created if absent.
   - A key pair `cs-aws-generated-key-<region>-<machineId>`. If its private key is not saved locally, any old pair is
     deleted and AWS creates a new ed25519 pair. The private key is saved with mode `0600` beside the session SSH keys.
     The name does not include the AWS account. A saved private key skips the check. So after you sign in to another
     account, launches fail in a region where this machine already holds a key. They fail until that key file is
     removed.

   If this setup fails, it is retried on the next launch.
3. **Poll.** Every 5 s the monitor calls `Ec2Backend.tick`. It reads the instance with `DescribeInstances`. It
   records the instance's public IP when it changes.
   - The session stays `preparing` until three things hold: the instance is `running`, it has a public IP, and that
     IP's port 22 accepts a connection within 3 s.
   - Then `connectionInfo.sshPort` is set and the session becomes `ready_to_connect`. `syncSshConfig` writes its
     per-session SSH host: public IP, port 22, the image's login user and this machine's key pair for the region.
   - While signed out of AWS, or before a stored key is restored, `tick` does nothing. The session keeps its status.
4. **Connect.** Opens the window at `/home/<login user>`. This is the `rootFolder` set when the record is created.
5. **Stop.**
   1. Wait for a pending boot to finish.
   2. Call `StopInstances`.
   3. Read the instance every 5 s until it is `stopped` or `terminated`.

   An instance already `stopped`, `terminated` or no longer listed ends the Stop at once. Before the stop is sent, a
   failed read or a failed `StopInstances` fails the Stop and leaves the instance running. After the stop is sent, a
   failed read is retried, with no limit. A reload during a stop resumes it, as with a Slurm stop.
6. **Delete.** Calls `TerminateInstances` if the signed-in account lists the instance. An instance in another AWS
   account is left running. Only the record is removed.

## Instance states

EC2 states map onto Slurm job states (`observedEc2`, `sessionMachine.ts`). So `deriveStatus` needs no EC2 case:

| EC2 state | Reads as |
|---|---|
| `pending`, `running`, `stopping` | `RUNNING` |
| `stopped` | `CANCELLED`. The session is `stopped`. |
| `shutting-down`, `terminated` | `FAILED`. The session is `failed`. |
| not listed by `DescribeInstances` | `FAILED`, as `terminated` |

## Tags and adoption

Each instance carries two tags:

- `Name` = its per-session SSH host name;
- `CS-Bridge-User` = the image's login user.

Adoption runs on each sign-in in a window that is not a session's remote window. This includes that window's restore
at activation. It scans every region for pending, running, stopping and stopped instances that carry `CS-Bridge-User`.
It adds a session for each one whose instance id and `Name` match no record. Other windows do not learn of the
sign-in.

An adopted instance has no image recorded. So it cannot be relaunched once terminated. Its SSH host names this
machine's key pair for the region. So an instance launched from another machine refuses the connection.
